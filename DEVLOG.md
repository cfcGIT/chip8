**Goal:** Load a ROM and run the 6 opcodes needed for the IBM logo.

**What works**
- ROM loading at 0x200, fetch-decode-execute loop
- Opcodes: 00E0, 1NNN, 6XNN, 7XNN, ANNN, DXYN
- Displays the logo in the console with '#' and '.' at 60 Hz, running 12 instructions per frame.

**What broke and why**
1. The logo was drawn and cleared in a loop. Two causes: PC was incremented after executing, so 1NNN jumped to the target and then skipped 2 bytes past it; and I reset PC to 0x200 when it reached the end of the ROM. The CPU ended up executing sprite data as code until it wrapped around to 00E0. Fix: increment PC right after the fetch, so jumps simply overwrite it, and remove the manual reset. The CPU doesn't know where a ROM ends: a program "ends" by jumping to itself.
2. At first I iterated through the entire RAM in a single step. Then I understood that there are two different clocks and each step is a single instruction execution. main() runs several steps per frame before rendering.

**Mistakes caught in code review** (by Claude Code; I fixed them myself before they caused visible bugs)
1. The V registers were stored in RAM (0x000–0x00F). It worked by accident, because that area is unused, but registers and memory are separate state: mixing them would break save states and the future Python bindings. Moved them to a dedicated 16-byte array.
2. The draw flag was cleared at the start of every instruction. With one step per frame it worked, but with 12 steps per frame a DXYN early in the frame would be overwritten by the next instruction and the redraw lost. Now the core only sets the flag and the front-end clears it after rendering.
3. DXYN didn't clip at the screen edges. The IBM logo never triggers it, but a sprite near the right edge would wrap into the next row, and near the bottom it would index past the end of the framebuffer (undefined behaviour). Fixed; to be verified with the Timendus quirks test.

**What I learned**
- Programs start in 0x200 because the COSMAC VIP interpreter was located in the first 512 bytes.
- I understand the full fetch-decode-execute loop.
- XOR drawing in DXYN: drawing a sprite a second time erases it (that's how games move sprites), and a pixel turned off sets VF, giving collision detection for free. Collision is not tested yet.
- Integer promotion: arithmetic on uint8_t/uint16_t is done in int, so storing the result back needs an explicit cast. MSVC only warns about it with extra flags (C4365 and friends are off even at /W4).
- Returning by value vs. by reference: `const auto& d = chip8.getDisplay();` does not avoid a copy if the function returns by value, because the reference binds to the temporary the function already created. The const reference has to be the return type.
